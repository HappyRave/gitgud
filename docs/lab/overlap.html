R11 · Overlap radar

Brief (Max, 2026-11-26): "1 Overlap radar", picked from the VEX analysis: warn while you work when a file you're changing has also changed on the remote, before it turns into a conflict. Locks can't do this job here: the VEX repos are on Bitbucket Cloud, which has no LFS lock API (O1, decided 2026-11-21), and no .gitattributes marks anything lockable.
Every number below was measured on 2026-11-26 from your D:\VEX clones (hyperdash, playfield, escape1, last 90 days, read only). People are shown by the initials the team already uses in commit subjects. Times and author pairings inside the mocks are placeholders.

What every variant shares

proposal
  • The overlap: files you changed (working copy + your unpushed commits) ∩ files changed on your upstream (origin/PartyGame) since the merge base, read from the commit graph after each fetch. .meta pairs fold into their asset. No server, no API: plain git, so Bitbucket is fine.
  • Risk by kind: !won't merge for files git can't merge as text (LFS, binary; Unity YAML in LFS goes to R9's merge by property); ~may conflict for text files where both sides touched the same lines; ✓merges when the changes are in different places (from merge-tree, already used for merge prediction).
  • Who and when come from the commits: "JG · 40 min ago · 2 commits". Click → their change in the usual viewer (diff, 3D compare, YAML structure).
  • The fix is a pull, with your edits stashed and put back (existing pull + strategy dialog). If a scene both sides changed has to merge, R9's table opens.

B

Heads-up when it starts

decided 2026-11-26 · "B Heads-up"

A's marks, plus one interruption at the moment it's cheapest: when a file you just started changing has new commits on origin, or origin changes a file you're already in. It speaks only for files that won't merge (LFS scenes, prefabs, assets, binaries); code that may conflict stays a mark. The heads-up is a toast in gitgud and a Windows notification when gitgud is in the background, since you're in Unity at that moment, not in gitgud.

Good at

  • Speaks at the cheapest moment, the only one that saves the hour.
  • Quiet where git copes: 75 of the 134 overlapping files were text, which git merges line by line.
  • Works with Max alone running gitgud; nothing for the team to install.

Costs

  • "Started editing" is seen by the file watcher when Unity saves, not when you open the scene. A long unsaved session is invisible until the first save.
  • Needs fresher data than the 10-min background fetch: see question 3.
  • A notification is one more thing that can nag; one per file and commit, with "Not now".
Claude's pick: B. The cost is the work done between origin's change and your merge, and only B reaches you inside that window, while you're in Unity. It's A plus one channel, so building it is A's work plus the trigger and a notification.

D

Soft claims

proposal

Locks without a lock server: "I'm on Lobby.unity" is written to a small ref pushed to origin (refs/gitgud/claims, a plain git object, works on Bitbucket). Every gitgud that fetches sees it on the file row, the moment you claim, before you save anything. Released on push, or after a day.

Claims only work between people running gitgud. Sourcetree and Unity don't see them, and nothing stops a commit.

Good at

  • The only variant that covers unsaved work, the 9:00 case: the claim exists before the first save.
  • Feels like the locks Bitbucket can't give.

Costs

  • Worthless until the team uses gitgud; today that's you. A claim nobody else sees is a note to yourself.
  • Stale claims (forgot to release, went on holiday) erode trust fast.
  • A ref under refs/gitgud/ pushed to a shared repo: needs the team's OK.
