R9 · Merge by property

Brief (Max, 2026-11-26): "if I push one field change in a scriptable object, and Miguel push another change of another property in the same file, I'm gonna get a merge conflict because it's considered binary data, instead of a clean merge because the 2 properties were independant" … "a big .unity file is on LFS, but it's basically a yaml with properties we can edit?" … "the merge shouldn't be automatic. You get a conflict as "normal", and an option to merge inteligently (with clear feedback of the changes and merged result)".
decided 2026-11-26 Not automatic: the file stops as a normal conflict, and merging by property is something you choose to do, with what changed and the merged result shown.
Example: BoatAttack's level_Island.unity, stored in LFS, merging miguel/lighting into main. You moved things and tuned spawns; Miguel relit the scene. 14 of the changes are only yours, 9 only his, and 4 clash. People, branches and values are invented.

What every variant shares

proposal
  • Where it's offered: on a conflicted file stored in LFS whose base, yours and theirs are all Unity text YAML (scenes, prefabs, ScriptableObjects, materials, controllers). Today these open in the pick-a-side view; that view gets the offer (E).
  • Matching: objects by fileID, properties by path. Lists of references (children, components) merge by ID; lists of values merge by position only when one side changed them, else it's a clash. Prefab overrides (m_Modifications) by target + property path.
  • A clash is: both sides changed the same property to different values; an object one side deleted and the other edited; or both sides inserted children under the same parent (the sibling order isn't knowable).
  • Every change is shown and reversible. One-sided changes come in applied; each can be flipped back. Clashes block "Save and mark resolved" until picked, like R4-A's flags.
  • Saving writes the merged YAML; git's LFS filter stores it as a new object when it's staged. The post-merge check (no broken references, no duplicate fileIDs) runs on the result. Every pick and the save are undoable (Ctrl+Z).
  • Also in rebase and cherry-pick stops, same view.
E

The offer, in the conflict

proposal

The file opens as it does today: an LFS conflict, pick a side. Above the two side cards, gitgud says what a property merge would do, counted when the conflict opens (both versions are parsed in the background). Nothing changes until you click.

M1

Three lists

proposal

Your words drawn literally: "From you", "From miguel/lighting" and "Clashes" side by side. Each change is a line (object › component › property, old → new) with a switch to leave it out. Clashes get the two values to pick from. The result preview opens from the header (Structure or 3D).

Good at

  • Answers "what did each of us change?" at a glance; the counts are the column heads.
  • Reading Miguel's work alone is easy: one column.

Costs

  • A new layout next to R4-A's table: two ways to resolve Unity files.
  • The same object's changes are split across columns (Crane: position in yours, mass in his).
  • Narrow columns cut long property paths.

M3

Scene tree

proposal

Unity's own shape: the merged scene's hierarchy on the left with a mark per object (yours, theirs, clash, added, deleted), an inspector in the middle for the selected object (each changed field with its source and a pick), the 3D result on the right.

Good at

  • Reads like Unity: added, moved and deleted objects are obvious.
  • All of one object's changes together.

Costs

  • Two clicks per change (object, then field); no list of everything.
  • Close to R4-C, which you didn't choose for conflicts.
  • Less useful for a ScriptableObject (one object, no hierarchy).
M2

States, drawn on the pick

proposal

1 · Deleted on one side, edited on the other

You deleted OldPier; Miguel changed its light. That's a clash at the object level: keep it deleted (his edits are dropped, and listed) or restore it with his changes.

2 · Both added children under one parent

Both objects are kept; only the order among Buoys' children is the question. In Unity the order shows in the hierarchy and in anything that reads children by index.

3 · Can't merge by property yet

Miguel's version isn't downloaded from LFS yet, so it can't be read: fetch it, then the counts appear. If a version is binary-serialized (Asset Serialization not set to Force Text when it was saved), the offer is replaced by a reason and pick-a-side stays.

4 · Every clash picked

The summary says where every change in the result came from, and what the check found. Save writes the file and stages it (stored in LFS again); the merge banner's Commit merge unlocks when no files are left.

Open questions

  1. Which layout: M1 Three lists, M2 R4-A table with every change, or M3 Scene tree? Claude's pick: M2 one resolver for every Unity file, with all three values on each row.
  2. One-sided changes: come in applied (flip any back), or each must be ticked before saving? Claude's pick: applied they're what a text merge would take without asking; only clashes block. Ticking 23 rows to approve them adds clicks without adding safety.
  3. Both sides added children under one parent: ask for the order (state 2), or yours first without asking? Claude's pick: ask it's rare, and order can matter to scripts.
  4. Count the changes when the conflict opens (E), or only after clicking "Merge by property"? Claude's pick: when it opens in the background; "4 clash" vs "0 clash" is what tells you whether it's worth it. A 50 MB scene takes a second or two.
  5. Offer it also for Unity YAML that isn't in LFS, when Smart Merge isn't set up or gives up? Claude's pick: yes same engine, and it removes the dependency on Unity's merge tool for anyone without the Hub.
