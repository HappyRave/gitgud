Round 4 · 2026-11-21 · decided: A

R4 · Merge conflicts, Unity first

What you see after "Merge conflict/theirs into conflict/ours" stops on conflicts, the same pair as the hands-on round: Engine.cs (code), ReplayCameras.prefab (Unity YAML), a prefab instance, and the LFS texture. Facts from the spike that every variant builds on: gitgud registers UnityYAMLMerge itself (with --force, untracked config only); it merges most prefab changes cleanly; on a real conflict --describe names the object, component and property; and in one case (both sides change the same override) it silently keeps yours and drops theirs, so gitgud compares both sides after every automatic merge and flags "merged, verify". Common to all: the R1 banner with Continue / Abort, and the conflict list sorted by kind on the left.

R4-A

Property table

decided 2026-11-21 · "A, as picked"Claude's pick

A Unity file opens as a table, one row per changed property: object › component › property, then base, yours, theirs and the result. Real conflicts sit on top with pick buttons (1 yours, 2 theirs, E edit); what Smart Merge merged on its own is listed below, collapsed, so you can check it. fileIDs are resolved to GameObject names; the raw YAML is one tab away.

Good at

  • Reads like Unity, not like YAML: "BlimpCamera › Transform › Position.x".
  • Shows what the automatic merge did, which is where the silent loss hides.
  • Dense and keyboard-driven: ↑↓, 1/2/E, Ctrl+↵ marks the file resolved.

Costs

  • Needs gitgud to parse Unity YAML and resolve fileIDs (part of the planned structural diff, Q6).
  • Large structural changes (whole objects added) read better in a tree (C).
Claude's pick: it's the only variant that shows the automatic merge's work next to the real conflicts, which is exactly where the spike found data loss. It reuses the --describe output and the prefab object list you already chose for the MVP (Q6), and it stays dense and keyboard-first like the rest of gitgud.
R4-B

Annotated text

not chosen

One resolver for everything: the familiar 3-way text merge (yours | result | theirs, arrow per hunk, as in Sublime Merge). For Unity YAML, gutter labels translate fileIDs into names ("BlimpCamera › Transform") so the text is readable. Smart Merge runs first; what's left shows as normal conflict hunks.

Good at

  • One tool to learn for code and assets.
  • Least new code: a text merge with labels.

Costs

  • Smart Merge leaves some conflicts with no markers at all (spike S2), so the text view has nothing to show; gitgud would have to re-create markers.
  • The automatic merges stay invisible, so the silent loss (S5) is only a warning, not something you can see.
R4-C

Two hierarchies

not chosen

Looks like Unity's own editor: yours and theirs as two hierarchy trees side by side, changed objects marked, objects only one side added shown as such. Select an object and the panel below shows its components with both values and a pick per field.

Good at

  • Familiar to anyone who knows the Unity hierarchy; good for added or moved objects.
  • Structure first: you see which objects changed before any field.

Costs

  • Two levels of clicking (object, then field) for a one-value conflict.
  • Least dense; a scene with hundreds of objects needs filtering.
R4-D

One at a time

not chosen

A guided pass through every conflict across all files, one per screen: big cards for base, yours and theirs, keys 1 / 2 / 3, then the next conflict. The progress bar spans the whole merge. Tower's conflict wizard taken to its end.

Good at

  • Hard to miss anything: every conflict and every "verify" gets its own stop.
  • Calm for scary merges; good for artists later (Q3).

Costs

  • Slow for a merge with many small conflicts.
  • No overview: you can't see related changes on the same object together.
R4-A

States, drawn on the pick

proposal

1 · Merged automatically, but verify

The spike's S5 case: both branches changed the same override on a prefab instance; Smart Merge reported a clean merge and kept yours. gitgud compares both sides, finds the overlap and flags the file. You keep yours or take theirs; the merge can't be committed until each flag is looked at (question 4).

2 · A code file in the same list

Engine.cs is plain text, so it opens the 3-way text merge: yours | result | theirs, an arrow per hunk, "Use both" for the common case of two added lines.

3 · An LFS texture

Binary files can't merge: pick a side with the image diff from round 1 (side by side, swipe, onion). If the file is lockable and someone holds the lock, that shows here too.

4 · Smart Merge not set up yet

First merge in a Unity repo: gitgud found Unity 6000.3 in the Hub and offers to register the driver for this repo (writes only .git/config and .git/info/attributes, nothing tracked). Without it, Unity files fall back to plain text conflicts.

5 · All resolved

Every file resolved and every flag checked: the summary says what happened (auto-merged, picked, verified), the post-merge check has re-read the prefabs, and Commit merge is the one primary action. Ctrl+Z after committing undoes the whole merge.

R4 · Verdict

decided 2026-11-21
  1. Variant: A, Property table. Max: "A, as picked".
  2. Smart Merge is offered at the first merge that hits Unity files (state 4).
  3. Automatic merges are listed, collapsed under the real conflicts.
  4. "Merged, verify" flags block Commit merge until confirmed.
  5. Code conflicts use three columns: yours | result | theirs.

Round 3 · 2026-11-21 · decided: A

R3 · Many projects

How gitgud holds 150+ repositories and switches between them. Your brief: "a lot of them, ideally folders or categories", several open at once as tabs. Common to every variant: open repos are tabs above the window (Ctrl+Tab cycles, Ctrl+W closes), Ctrl+P is a fuzzy "go to repo" from anywhere, and a repo's status in lists comes from a cache, refreshed when you look at it, so 150 repos never run 150 git status calls at startup. Repo names below are invented.

R3-A

Library tab + folders

decided 2026-11-21 · "A, as picked"Claude's pick

The first tab is always the Library: a full-window list of every repo with its status (branch, changes, ahead/behind, locks you hold, last activity, host). On the left, your own folders, nestable, drag repos between them, a repo lives in one folder. Below them, smart filters that fill themselves: Dirty, Ahead, Locks held, Unity, Missing on disk. Inside a folder, each subfolder shows its most recently used repos first, with "show all" to expand. Type anywhere to filter; Enter opens the repo in a new tab.

Good at

  • Folders exactly as you asked, with an overview of all 150 at once.
  • Smart filters answer "what did I leave uncommitted / unpushed / locked?" across every project.
  • Same table look as the rest of gitgud: dense rows, sortable columns.

Costs

  • A whole tab for the library; switching repos from inside a repo goes through Ctrl+P or the tab bar.
  • Folders are manual work at first (the scan in state 3 suggests them).
Claude's pick: it's the one that gives you folders and a cross-repo status overview in one place, and it costs nothing inside a repo, where layout A from round 1 stays untouched. Ctrl+P covers the fast switch, so the library only has to be good at organizing.
R3-B

Project rail

not chosen

A narrow project tree is always on screen, left of the repo's own sidebar: folders collapse, open repos are bold, a dot shows uncommitted work. Click a repo to switch; there are no tabs, the rail is the tab bar. A search field at the top of the rail filters it.

Good at

  • Switching is one click from anywhere, with folders always visible.
  • Dirty dots across projects without opening a library.

Costs

  • Two trees side by side (projects, then branches) cost ~200 px on every screen.
  • 150 repos don't fit; you live in the search field or collapse most folders.
R3-C

Switcher + tags

not chosen

No library screen. Ctrl+P opens a switcher over whatever you're doing: recents first, then matches, each with its status. Categories are tags instead of folders, so a repo can be both "Studio" and "Unity" and "VR"; type #vr to filter by tag. Tags are edited from the switcher row.

Good at

  • Fastest for a keyboard user who knows what they want.
  • Tags fit repos that belong to several categories.

Costs

  • No overview: you can't browse 150 repos or see which ones are dirty at a glance.
  • Tags are less tidy than folders; no hierarchy.
R3-D

Smart groups only

not chosen

The library of A, but you never sort anything by hand. Groups come from facts gitgud already knows: where the repo is on disk, which host and owner its remote has, what kind of project it is (Unity, Rust, web), plus pins. Move a folder on disk and the grouping follows.

Good at

  • Zero upkeep with 150+ repos.
  • Groups are always true; nothing goes stale.

Costs

  • Not what you asked for: no categories of your own ("client work", "jam games").
  • Groups follow your disk layout, so a messy disk gives a messy library.
R3-A

States, drawn on the pick

proposal

1 · Ctrl+P from inside a repo

The fast path that every variant shares: from any tab, Ctrl+P, type a few letters, Enter. The folder shows as a prefix, status on the right; already-open repos jump to their tab instead of opening a second one.

2 · Twelve tabs open

Tabs shrink to the repo name, then overflow into a "+4" menu. A dot marks uncommitted work, a lock marks locks you hold. Tabs reopen on the next launch.

3 · Adding many repos at once

"Scan a folder" finds every repo under it, groups them by parent folder and suggests a gitgud folder for each group, so 37 repos get organized in one step. Repos it already knows are skipped.

4 · A repo moved or deleted on disk

The row stays where you put it, greyed, with "Locate…" and "Remove from gitgud". Nothing disappears silently, and the Missing smart filter collects them all.

R3 · Verdict

decided 2026-11-21
  1. Variant: A, Library tab + folders. Max: "A, as picked".
  2. One folder per repo, no tags.
  3. Folders nest freely.
  4. Library status is local only, no background fetch; "behind" shows its last known value and age, plus a manual "Fetch all visible". Not drawn yet.
  5. Reopen last session's tabs on launch, Library first.

Round 2 · 2026-11-21 · decided: A

R2 · History edits

How rewriting history works inside layout A: reword, squash, fixup, reorder, drop, with a preview of the result and conflict prediction before anything runs. The example is the same feature/stack from the hands-on round: a "rgiht" typo and a fixup! commit. Already decided and drawn into every variant: classic stop-on-conflict with prediction first (Q11), gitgud owns the rewrite logic (Q10), everything lands in the op log so Ctrl+Z undoes it (Q9). The 3-way / Smart Merge resolver is round 3.

R2-A

Plan beside preview

decided 2026-11-21 · "A, as picked"Claude's pick

"Edit history" on a branch turns the inspector into the rebase plan: one row per commit with an action key, drag handles and a per-step conflict prediction. The graph keeps showing the real history and draws the planned result as dashed "after" rows above the faded commits they replace. Nothing changes until Start. A neutral banner says you're planning.

Good at

  • Preview before rewrite (UX principle 4) without leaving layout A or opening a modal.
  • The whole edit is one list you drive by keys: P R E S F D, Alt+↑↓ to move.
  • Prediction per step tells you which commit would conflict, before you start.

Costs

  • The graph gets busier while planning (dashed and faded rows together).
  • A one-key reword of the tip still goes through the plan (see question 5).
Claude's pick: it's the only variant that shows the result before anything runs and keeps you in the R1 layout. The plan is Fork's todo list (the best of the hands-on round), the preview is in the graph you already trust, and Ctrl+Z still covers you after Start.
R2-B

Edit in place

not chosen · kept for single-commit edits

No plan at all. Every edit happens on the graph row and applies immediately: R renames inline, F folds into the parent, drag a commit onto another to squash, Alt+↑↓ to move. Safety comes from the op log instead of a preview: each action is one Ctrl+Z away (GitButler and Tower style).

Good at

  • Fastest: a typo fix is R, type, Enter.
  • Nothing to learn: the graph is the editor.

Costs

  • No preview of a multi-step edit; you see the result after each step.
  • A conflict can stop you in the middle of a sequence you meant as one change.
R2-C

Plan dialog

not chosen

Fork's model, the best rebase UI of the hands-on round: a modal with the todo list (autosquash pre-applied, single-key actions, inline reword) and the selected commit's diff below it. Start runs the whole plan.

Good at

  • Proven: you've used this shape in Fork.
  • Room to focus: the dialog hides everything else.

Costs

  • The graph is hidden behind the dialog, so there's no picture of the result.
  • Modal: you can't look at another commit while planning.
R2-D

Now | After

not chosen

The preview is the main thing: the history pane splits into "now" and "after" side by side, each after-row saying where it came from ("← 3493748, reworded"). Pick a commit on either side and the inspector shows its actions. Teaches what a rebase does, at the cost of width.

Good at

  • Clearest picture of what changes: before and after never overlap.
  • Good for long plans (10+ commits) where dashed rows in one graph would blur.

Costs

  • Two half-width graphs: subjects truncate early.
  • Actions live in the inspector, one commit at a time; slower than a list with keys.
R2-A

States, drawn on the pick

proposal

1 · Conflict predicted

Rebasing feature/stack onto the newer master: the plan predicts that step 1 conflicts in Engine.cs (both sides edited line 6) and says which commit causes it. Start is still possible, but the footer offers the fixes first. The banner from R1 state 1 takes over only if you start anyway.

2 · Squash asks for the message

Squash (S) opens the combined message inline in the plan, both messages prefilled. Fixup (F) keeps the target's message and drops the other, so it needs no editor.

3 · Done

The branch now has 2 commits; origin/feature/stack still points at the old 3, drawn faded so the divergence is visible. The inspector offers Undo and "Force-push with lease"; there's no "update from remote" button that would pull the old commits back (a GitButler footgun from the hands-on round).

R2 · Verdict

decided 2026-11-21
  1. Variant: A, Plan beside preview. Max: "A, as picked".
  2. fixup! / squash! are applied automatically when the plan opens.
  3. Plan order: newest first, like the graph.
  4. After rewriting a pushed branch: offer "Force-push with lease" right away.
  5. Single-commit edits (reword the tip, fixup or drop one commit) apply at once, Ctrl+Z undoes; anything bigger opens the plan. Not drawn yet.

Round 1 · 2026-11-21 · decided: A

R1 · Main window layout

Four ways to arrange the screen you live in: commit graph, working copy and staging, diff, op log (undo history), LFS locks and agent proposals. Built on the decisions already made: undo is an op log behind Ctrl+Z, hunks get stage buttons on their own row, agent work arrives as proposals, locks show on file rows.

R1-A

Graph centre

decided 2026-11-21 · "A, as picked"Claude's pick

The graph is always the middle. Selecting the top "uncommitted" row turns the right-hand inspector into staging (unstaged / staged lists, diff with per-hunk buttons, commit box); selecting a commit turns it into that commit's diff. The sidebar holds branches, stashes, locks and agent proposals. The op log is one click away in the sidebar and always summarised by the Undo button.

Good at

  • History never leaves the screen, so rebases and undo are visible where they happen (P3).
  • Closest to Sourcetree and Fork: lowest switching cost.
  • One selection model: pick a row, the inspector follows.

Costs

  • Inspector is ~45% of width; long lines in the diff wrap or scroll sooner than in B.
  • Staging is one click away from the graph, not the default view.
Claude's pick: it keeps the graph (your safety net for history edits) and staging on one screen without modes, and it's the shape you already know from Sourcetree, so every new idea (locks, proposals, op log) lands in a familiar frame.
R1-B

Stage desk

not chosen

Working on changes is the main job, so the working copy owns the screen: file lists on the left, a wide diff in the middle with all changed files in one scroll (Sublime-style), and the graph as a narrow rail on the right. Click a commit in the rail and the middle shows it; Esc returns to the desk.

Good at

  • Widest diff: best for hunk staging and texture previews.
  • Fastest daily loop: open, stage, commit without a single navigation.

Costs

  • The narrow rail hides authors, hashes and long subjects; history edits need a wider view.
  • Locks and proposals have no permanent home; they go into the branch menu and a badge.
R1-C

One timeline

not chosen

The boldest one. A single column holds everything that happened or might happen, newest first: pending agent proposals at the top, then your uncommitted work, then commits, with op log entries woven in as thin rows ("you discarded Engine.cs · Restore"). No sidebar: branches are chips and the palette. The right side is the detail for whatever row is selected.

Good at

  • Undo is part of history, not a separate panel: you see what you did right next to what it changed.
  • Agent proposals sit exactly where they would land.
  • Nothing to learn: one list, one detail.

Costs

  • Op rows interleaved with commits can get noisy during busy sessions (needs a filter).
  • No sidebar means locks and stashes live behind chips; multi-branch overviews are weaker.
  • No tool does this today, so it's the least proven.
R1-D

Tiles

not chosen

lazygit's model as a desktop app: five numbered tiles on the left (status and locks, files, branches, commits, stash and op log), one big main view on the right. Keys 1–5 jump between tiles, single-letter verbs act on the focused one, and the footer always lists the keys that work right now. The mouse still works everywhere.

Good at

  • Most keyboard-friendly: every state shows its keys.
  • Everything visible at once at a glance, nothing hidden in a sidebar tree.

Costs

  • Each tile is small; the graph gets ~10 rows instead of ~25.
  • Feels like a terminal app; less room for previews and the 3-way merge.
R1-A

States, drawn on the pick

proposal

The screens that matter beyond the happy path. If you pick another variant, these move with it.

1 · Mid-rebase with conflicts

A banner owns the top while the rebase is running, with Continue / Skip / Abort. Conflicts are sorted by kind so each goes to the right resolver: code to the 3-way merge, Unity YAML to Smart Merge with mine/theirs, LFS binaries to a side pick with previews.

2 · Editing a file someone else locked

Locks show in the sidebar and on file rows. Editing a file locked by someone else raises an inline warning on the row, not a modal, with the two things you can do about it.

3 · Agent proposal waiting

A proposal is a ghost row at the top of the graph and an item in the sidebar. The inspector shows message, the agent's reason, risk flags (flagged, never blocked) and per-hunk ticks; Approve commits through the git CLI.

4 · Detached HEAD, fetch running

Detached HEAD replaces the branch pill in warning colour with "Create branch here". Background jobs (fetch, LFS download) report in the status strip with real numbers, never a blocking dialog.

5 · Clean tree, longest branch name

A 64-character branch name truncates in the middle so both the folder and the ending stay readable. Nothing to commit: the inspector says so and points at the last action you can undo.

6 · Op log open

The op log (Ctrl+3) lists every action with the files it touched; Restore works on any entry, discards included. The graph stays visible beside it.

Verdict

decided 2026-11-21
  1. Layout: A, Graph centre. Max: "A, as picked".
  2. Op log: its own panel (sidebar entry, Ctrl+3). Came with A.
  3. Locks and agent proposals: permanent sidebar sections. Came with A.
  4. Row height: 24 px default, with an app-wide Compact toggle (20 px).
  5. Ultrawide: above ~2400 px the inspector splits in two (file lists and commit box | diff). Not drawn yet.
